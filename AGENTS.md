Local Odoo Community 19 uses one application DB (`tacare_local`), three website records and shared `res.users` accounts. Native cookies remain domain-scoped. Recruitment and employee hiring are retired. ## Working rules

Read related manifests, models, controllers, views, security and workflow before editing. Prefer Odoo 19 Community modules (`website`, `portal`, `hr_recruitment`, `website_hr_recruitment`, `hr_skills`) and extend them in existing custom addons. Keep addon/model/XML IDs and dependencies. The target JSON model names conflict with existing `tacare.*` models; see `docs/database_mapping.md` before changing schema. Do not rename data models or run production migrations for UI changes. `res.users` is an account, `res.partner` a contact/organization, `res.company` an Odoo company scope, and `res.groups` Odoo access groups. Role alone never proves record ownership. `care.org.member` is the intended organization boundary; existing business accounts have a commercial-partner fallback until migration is approved.

Role policy updated by the owner on 22 October 2026: businesses use Kho + TA.CARE; individuals and system admins use all three. Other product homepages stay public, but product functions require a permitted login on the server, including namespace access under another host. SSO now uses first-party, browser-bound handoffs after complete native authentication. Admins synchronize three sites, businesses Kho + TA.CARE, individuals all three. Logout revokes the server-side `care.auth.session` group immediately; open tabs refresh on status/focus. Other browsers/devices have separate groups. Never put passwords, native session IDs or grant credentials in URLs. `care.auth.handoff` is one-use, short-lived and bound to the target session nonce and authenticated source; portal ACLs grant no direct access to these models. Login dialogs submit the native Odoo /web/login form with CSRF/CAPTCHA/MFA intact. Tủ Hồ Sơ defaults to the owner library for regular accounts and exposes an explicit all-profiles tab only to admins, scoped to the admin’s allowed companies rather than only the active company; direct profile/service URLs are owner/admin scoped; separately authorized Kho candidate views retain consent checks. Demo seed is manual and local-only; credentials stay in ignored backups. Every write route must check authenticated role, record ownership, allowed fields and current state on the server. Portal direct ACLs are read-only and record-scoped; controller `sudo()` is only acceptable after narrow, explicit authorization and a scoped record lookup. Hidden buttons are not permissions. Contact access requires `care.consent` with purpose `contact`, the exact organization, field `email`, and an accepted connection. Profile discovery/matching requires current purpose-specific consent. Do not put real personal data, passwords or uploaded files in fixtures, logs or screenshots.

Kho membership owners have both recruitment capabilities; existing active `recruiter` members retain applicant handling, and admins can set `can_manage_jobs` and/or `can_handle_candidates` for other combinations. Legacy business accounts without membership retain the existing commercial-partner fallback until migration is approved. Four sector examples are catalog/validation examples, not employer fixtures. Ignored `backups/` and `runtime/` may contain local QA credentials; never commit or print them. Missing profile data is unknown, not a failed criterion; Kho does not display a percentage matching score.

Use Vietnamese labels, real logos, shared design tokens, responsive layouts, visible focus, labelled forms, retained input on validation errors and reduced motion support. Use real source-documented photographs, no AI photos. Only Kho and Tủ have carousels; their photo sets and compositions must differ. On 22 October the owner approved the Kho and Tủ homepage bodies and explicitly requested a TA.CARE redesign plus clearer navigation and interiors. Preserve the Kho homepage body; on 23 October the owner subsequently requested a new Tủ library structure (see below). The current TA.CARE `hx-*` homepage presents both sides of seasonal matching without a photo carousel. See `docs/research/navigation_interiors_2026-10-22.md`. Seasonal shared-profile details use `/tacare/matching/<job_id>/profile/<profile_id>` with owner/organization and current discovery/matching consent checks; the retired recruitment URLs stay blocked. The owner subsequently requested a Tủ overview homepage and removal of the carousel inside the profile library; do not restore the library carousel. Do not use decorative arrow text glyphs on Kho; show the current navigation/tab with accessible selected states. See `docs/prototype.md`, `docs/backend_local.md` and `docs/database_mapping.md` for design and implementation limits. The standalone `prototype/` holds fictional examples and is not Odoo login or storage. Do not report OCR, persisted matching snapshots, audit/outbox workers, or CV upload as integrated until their routes and tests exist.

Run local Odoo with `docker compose up -d db tacare gateway`; open the three `*.localhost:8069` URLs in `docs/backend_local.md`. After a local DB backup, update changed addons with `docker compose run --rm tacare -c /etc/odoo/local.conf -d tacare_local -u tacare_account_access,tacare_website --stop-after-init`, then restart `tacare`. The independent design demo runs with `python3 prototype/serve.py`. Validate Python/XML, Docker HTTP routes, role checks and form flows. The rollback-only ORM security check is `tacare_website/tests/dev_schema_check.py` and runs inside Odoo shell. ## Production deploy contract

`.github/workflows/deploy-tacare.yml` runs on pushes to `main` and manual dispatch. It passes the exact commit SHA over SSH to the server's root-owned `/usr/local/lib/tacare-deploy/deploy.sh`; the server fetches and deploys only addons under `source/apps/tacare/addons/`. The current server deploy scripts live outside this repository and must be inspected before changing them. Do not push `main` as a routine check: it starts a production deployment.

The server's HTTP probe requires these rendered homepage classes: `tc-hub` on `tacare.vn`, `tc-jobs` on `khovieclam.vn`, and `tc-profiles` on `tuhoso.com`. Preserve them when replacing a homepage template; verify all three against local HTTP after updating the addon. Do not weaken the probe to hide a missing marker. The deploy worker stages in an isolated PostgreSQL cluster, neutralizes that copy, then gates a backed-up production update; server config, Odoo core, Python dependencies, Docker and Nginx are outside automatic addon scope. A failed staging probe means production was not changed. See the deployment workflow before editing release behavior.
