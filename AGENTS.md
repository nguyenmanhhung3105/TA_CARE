## Working rules

Read related manifests, models, controllers, views, security and workflow before editing. Prefer Odoo 19 Community modules (`website`, `portal`, `hr_recruitment`, `website_hr_recruitment`, `hr_skills`) and extend them in existing custom addons. Keep addon/model/XML IDs and dependencies. The target JSON model names conflict with existing `tacare.*` models; see `docs/database_mapping.md` before changing schema. Do not rename data models or run production migrations for UI changes. `res.users` is an account, `res.partner` a contact/organization, `res.company` an Odoo company scope, and `res.groups` Odoo access groups. Role alone never proves record ownership. `care.org.member` is the intended organization boundary; existing business accounts have a commercial-partner fallback until migration is approved.

Role policy updated by the owner on 22 October 2026: businesses use Kho + TA.CARE; individuals and system admins use all three. Other product homepages stay public, but product functions require a permitted login on the server, including namespace access under another host. SSO now uses first-party, browser-bound handoffs after complete native authentication. Admins synchronize three sites, businesses Kho + TA.CARE, individuals all three. Logout revokes the server-side `care.auth.session` group immediately; open tabs refresh on status/focus. Other browsers/devices have separate groups. Never put passwords, native session IDs or grant credentials in URLs. `care.auth.handoff` is one-use, short-lived and bound to the target session nonce and authenticated source; portal ACLs grant no direct access to these models. Login dialogs submit the native Odoo /web/login form with CSRF/CAPTCHA/MFA intact. Tủ Hồ Sơ defaults to the owner library for regular accounts and exposes an explicit all-profiles tab only to admins, scoped to the admin’s allowed companies rather than only the active company; direct profile/service URLs are owner/admin scoped; separately authorized Kho candidate views retain consent checks. Demo seed is manual and local-only; credentials stay in ignored backups. Every write route must check authenticated role, record ownership, allowed fields and current state on the server. Portal direct ACLs are read-only and record-scoped; controller `sudo()` is only acceptable after narrow, explicit authorization and a scoped record lookup. Hidden buttons are not permissions. Contact access requires `care.consent` with purpose `contact`, the exact organization, field `email`, and an accepted connection. Profile discovery/matching requires current purpose-specific consent. Do not put real personal data, passwords or uploaded files in fixtures, logs or screenshots.

Kho membership owners have both recruitment capabilities; existing active `recruiter` members retain applicant handling, and admins can set `can_manage_jobs` and/or `can_handle_candidates` for other combinations. Legacy business accounts without membership retain the existing commercial-partner fallback until migration is approved. Four sector examples are catalog/validation examples, not employer fixtures. Ignored `backups/` and `runtime/` may contain local QA credentials; never commit or print them. Missing profile data is unknown, not a failed criterion; Kho does not display a percentage matching score.
