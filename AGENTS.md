# TA.CARE repository guide

TA.CARE connects people, demonstrated skills and opportunities through Kho Việc Làm, Tủ Hồ Sơ and TA.CARE. Local Odoo Community 19 uses one application DB (`tacare_local`), three website records and shared `res.users` accounts. Native cookies remain domain-scoped. On 20 October 2026 the owner authorized browser-bound SSO to synchronize permitted website sessions and global logout within that browser; see `docs/research/implementation_sso_2026-10-20.md`.

Product scope clarified on 19 October 2026: recruitment is one part; flexible work connecting businesses or individuals with workers, including C2C, is a second part. The owner subsequently authorized code, local schema updates and a fictional demo dataset (20 jobs: 5 recruitment + 15 flexible; 15 profiles). Read `docs/project_scope.md` and `docs/research/implementation_flexible_demo_2026-10-19.md`. The flexible demo extends `hr.job` and existing `care.profile.capability`, uses static locations. On 20 October the owner explicitly authorized **multiple `tacare.profile` records per user** for distinct purposes; version 19.0.6.0.0 removes only the old SQL unique-user constraint and adds `profile_title`, keeping existing profile IDs and references. Read `docs/research/implementation_profile_refresh_2026-10-20.md`. Profile forms, children and consent must use an explicit owner-checked `profile_id`; never choose an arbitrary first profile for a multi-profile write. Flexible matching, maps, booking, payments and operating passenger transport remain outside this demo. Matching remains centered on TA.CARE; future suggestions must use the same policy and current consent. This authorization covers local demo work, not production deployment.

## Repository map

- `source/odoo-server/`: ignored Odoo 19 core checkout; read relevant code, never edit core.
- `source/apps/tacare/addons/tacare_account_access/`: `res.users.tacare_account_role`, website projection, login host restrictions, SSO handoffs and browser-group revocation.
- `source/apps/tacare/addons/tacare_website/`: QWeb pages, `hr.job`/`hr.job.skill` extensions, profile and connection models, consent, revision and other `care.*` schema, controller permissions and brand assets.
- Kho việc làm F01–F12 uses `care.job.sector`, `care.job.requirement`, organization membership capability flags and `care.audit.event.changes`. Read `docs/kho_viec_lam_traceability.md` and current DEV results in `docs/backend_local.md` before editing those flows.
- `source/apps/khovieclam/addons/`, `source/apps/tuhoso/addons/`: empty historical placeholders.
- `compose.yaml`, `compose.override.yaml`, `docker/`: local PostgreSQL, one Odoo service and Nginx gateway. `runtime/` and `backups/` hold ignored local data.
- `prototype/`: earlier standalone design demo with fictional seed data and a role switch; it does not authenticate with Odoo. `docs/`: audits and guides.

## Working rules

Read related manifests, models, controllers, views, security and workflow before editing. Prefer Odoo 19 Community modules (`website`, `portal`, `hr_recruitment`, `website_hr_recruitment`, `hr_skills`) and extend them in existing custom addons. Keep addon/model/XML IDs and dependencies. The target JSON model names conflict with existing `tacare.*` models; see `docs/database_mapping.md` before changing schema. Do not rename data models or run production migrations for UI changes. `res.users` is an account, `res.partner` a contact/organization, `res.company` an Odoo company scope, and `res.groups` Odoo access groups. Role alone never proves record ownership. `care.org.member` is the intended organization boundary; existing business accounts have a commercial-partner fallback until migration is approved.

Role policy reconfirmed by the owner on 20 October 2026: businesses use Kho + TA.CARE, candidates use Tủ + TA.CARE, only system admins use all three. Other product homepages stay public, but product functions require a permitted login on the server, including namespace access under another host. SSO now uses first-party, browser-bound handoffs after complete native authentication. Admins synchronize three sites, businesses Kho + TA.CARE, candidates Tủ + TA.CARE. Logout revokes the server-side `care.auth.session` group immediately; open tabs refresh on status/focus. Other browsers/devices have separate groups. Never put passwords, native session IDs or grant credentials in URLs. `care.auth.handoff` is one-use, short-lived and bound to the target session nonce and authenticated source; portal ACLs grant no direct access to these models. Login dialogs submit the native Odoo /web/login form with CSRF/CAPTCHA/MFA intact. Tủ Hồ Sơ defaults to the owner library for regular accounts and exposes an explicit all-profiles tab only to admins, scoped to the admin’s allowed companies rather than only the active company; direct profile/service URLs are owner/admin scoped; separately authorized Kho candidate views retain consent checks. Demo seed is manual and local-only; credentials stay in ignored backups. Every write route must check authenticated role, record ownership, allowed fields and current state on the server. Portal direct ACLs are read-only and record-scoped; controller `sudo()` is only acceptable after narrow, explicit authorization and a scoped record lookup. Hidden buttons are not permissions. Contact access requires `care.consent` with purpose `contact`, the exact organization, field `email`, and an accepted connection. Profile discovery/matching requires current purpose-specific consent. Do not put real personal data, passwords or uploaded files in fixtures, logs or screenshots.

Kho membership owners have both recruitment capabilities; existing active `recruiter` members retain applicant handling, and admins can set `can_manage_jobs` and/or `can_handle_candidates` for other combinations. Legacy business accounts without membership retain the existing commercial-partner fallback until migration is approved. Four sector examples are catalog/validation examples, not employer fixtures. Ignored `backups/` and `runtime/` may contain local QA credentials; never commit or print them. Missing profile data is unknown, not a failed criterion; Kho does not display a percentage matching score.

Use Vietnamese labels, real logos, shared design tokens, responsive layouts, visible focus, labelled forms, retained input on validation errors and reduced motion support. Use real source-documented photographs, no AI photos. Only Kho and Tủ have carousels; their photo sets and compositions must differ. TA.CARE restores its original orbit/story homepage without a photo carousel; preserve that design unless the owner requests a redesign. Tủ carousel precedes the profile library. Do not use decorative arrow text glyphs on Kho; show the current navigation/tab with accessible selected states. See `docs/prototype.md`, `docs/backend_local.md` and `docs/database_mapping.md` for design and implementation limits. The standalone `prototype/` holds fictional examples and is not Odoo login or storage. Do not report OCR, persisted matching snapshots, audit/outbox workers, or CV upload as integrated until their routes and tests exist.

Run local Odoo with `docker compose up -d db tacare gateway`; open the three `*.localhost:8069` URLs in `docs/backend_local.md`. After a local DB backup, update changed addons with `docker compose run --rm tacare -c /etc/odoo/local.conf -d tacare_local -u tacare_account_access,tacare_website --stop-after-init`, then restart `tacare`. The independent design demo runs with `python3 prototype/serve.py`. Validate Python/XML, Docker HTTP routes, role checks and form flows. The rollback-only ORM security check is `tacare_website/tests/dev_schema_check.py` and runs inside Odoo shell. Do not push, deploy, change DNS/TLS, touch production services or use a production DB without a separate request. Report exactly what ran and any limits.

## Production deploy contract

`.github/workflows/deploy-tacare.yml` runs on pushes to `main` and manual dispatch. It passes the exact commit SHA over SSH to the server's root-owned `/usr/local/lib/tacare-deploy/deploy.sh`; the server fetches and deploys only addons under `source/apps/tacare/addons/`. The current server deploy scripts live outside this repository and must be inspected before changing them. Do not push `main` as a routine check: it starts a production deployment.

The server's HTTP probe requires these rendered homepage classes: `tc-hub` on `tacare.vn`, `tc-jobs` on `khovieclam.vn`, and `tc-profiles` on `tuhoso.com`. Preserve them when replacing a homepage template; verify all three against local HTTP after updating the addon. Do not weaken the probe to hide a missing marker. The deploy worker stages in an isolated PostgreSQL cluster, neutralizes that copy, then gates a backed-up production update; server config, Odoo core, Python dependencies, Docker and Nginx are outside automatic addon scope. A failed staging probe means production was not changed. See the deployment workflow before editing release behavior.
